# 需求评估 01 · 自动记账（无障碍）

> 评估日期：2026-11-11
> 对应需求：第 1 条 —— 用支付宝/微信付款后，App 能自动识别并记账，尽量做到「无感」。
> 评估结论：**技术上可行，但不能保证 100% 无感、100% 不漏。推荐先做「探针」验证，再按“智能无感”方案落地。**
> **已拍板（2026-11-11）**：主方案 = A 无障碍读屏 + B 通知兜底 + C 账单导入兜底（C 你一般不用，降为后续可选，不占首期工期）；默认入账方式 = 智能无感；首期范围 = 支付宝/微信支付成功页 + 转账 + 红包；账单详情补记你担心误识别，首期不做，列为后续可选。
> 关联文档：[`开发文档.md`](./开发文档.md)、[`执行计划.md`](./执行计划.md)

---

## 0. 先看结论（30 秒版）

1. **能做。** 安卓的「无障碍服务」可以读取支付宝、微信支付结果页上的文字，从中提取金额、商户、支付状态，然后自动写入现有账本。钱迹、小账本、小星记账等产品都用了这个原理，属于成熟做法。
2. **做不到“绝对无感”。** 它依赖系统权限和支付 App 的页面，以下情况会漏记或记错：手机系统把后台服务杀掉、支付宝/微信改版、支付结果页一闪而过、淘宝等 App 屏蔽无障碍、金额或商户没有显示在页面上。
3. **最大的难点不是“读到金额”，而是“判断准不准、会不会重复记、分类对不对”。** 所以方案里必须有防重复、待确认、可撤销、分类学习这几道保险。
4. **建议的推进方式：** 先做一个 1~2 天的「探针版」，用你的手机在支付宝/微信真实支付 15~25 笔（可以每笔 0.01 元），把真实页面样本采集回来。确认能稳定读到金额和商户后，再投入正式开发；否则及时改用 OCR/账单导入等备选方案。
5. **已定方案：** A 无障碍读屏为主 + B 通知监听兜底 + C 账单导入兜底（C 你一般不用，放到后续可选）；默认使用「智能无感」：高置信自动记、低置信待确认、通知可撤销。详见 §5、§6。
6. **工作量预估：** 首期（支付成功页 + 转账 + 红包）约 10~15 个开发工作日；如果只先做支付成功页 MVP，约 5~8 个开发工作日。详见 §12。

## 1. 现有安卓版是什么状态

我查看了当前项目文档和代码：

- `android/` 是**原生 Kotlin + Jetpack Compose** 的安卓 App，不是小程序壳子。
- 按 `android/docs/开发文档.md` 和 `android/docs/执行计划.md`，P0~P9 已完成：本地数据库（Room）、云同步（CloudBase HTTP API）、首页/记账/账单/统计/分类/周期账单/待办/云同步/导出/照片/到期提醒，当前版本为 `1.0.0`（versionCode 1）。
- 现有代码里已经有这些可直接复用的能力：
  - `Repository.addRecord(...)`：新增一笔账单，自动走本地数据库和云同步。
  - `SyncManager.pushSoon()`：记完账自动排队上云，不影响界面。
  - `HomeScreen` 页脚「系统组」：已经有「外观 / 云同步 / 清除所有数据」入口，可加一行「自动记账」。
  - `ReminderScheduler` / 通知渠道：可复用做「自动记账服务状态提醒」。
  - `AppContainer`：手写的依赖装配，新模块直接挂进去即可。

**结论：自动记账是一个独立的新模块，不需要推倒现有安卓版重做；自动记出来的账和手动记的账走同一条路，因此天然支持三端同步。**

## 2. 自动记账是怎么工作的（通俗解释）

可以把整个链路想成四个角色：

| 角色 | 用大白话说 | 对应技术 |
|---|---|---|
| ① 速记员 | 只在你打开支付宝/微信的支付页面时，站旁边看你屏幕上的字 | 安卓「无障碍服务」（AccessibilityService） |
| ② 识别员 | 从一堆文字里找出「支付成功」「¥12.50」「星巴克」这些关键信息 | 本地页面解析规则（纯 Kotlin，不联网） |
| ③ 查重员 | 判断这笔是不是已经记过，防止同一笔支付记两遍 | 交易单号 / 金额+商户+时间指纹 |
| ④ 记账员 | 把金额、商户、分类写成一条账，交给现有账本 | 调用现有 `Repository.addRecord` |

需要特别说明：

- **不是破解支付宝/微信，也不是转你的钱。** 无障碍服务只「看」页面文字，不会点击付款、不会读取密码、不会操作支付 App。
- **所有识别在手机本地完成。** 屏幕文字不会上传到云端，只有最终生成的那条账单（金额、分类、备注等）会像手动记账一样同步。
- **系统会弹一个“此服务可以读取屏幕内容”的高危提示。** 这是安卓对所有无障碍服务的统一提示，不能绕过，用户必须手动同意。

## 3. 能覆盖到什么程度（按场景）

以下是**经验预估**，最终以 P-A0 探针在你手机上的实测为准：

| 支付场景 | 自动识别把握 | 说明 |
|---|---|---|
| 支付宝：扫商家码 / 出示付款码 | ⭐⭐⭐ 高 | 支付成功页通常有金额、商户名，最适合自动记 |
| 支付宝：App 内线上支付（跳到支付宝再跳回商家） | ⭐⭐ 中高 | 支付结果页可能一闪而过，有漏记可能 |
| 支付宝：转账给个人 | ⭐⭐ 中 | 首期支持；默认只记“转出”，不记“转入” |
| 微信：扫商家码 / 付款码 | ⭐⭐⭐ 高 | 同支付宝 |
| 微信：App 内线上支付 | ⭐⭐ 中高 | 支付结果页可能一闪而过 |
| 微信：发红包 / 转账 | ⭐ 中低 | 首期支持，但红包走“半自动确认”；红包流程特殊，往往要重新点开才看得到金额 |
| 退款 / 支付失败 / 取消 | ✅ 不会误记 | 识别到「退款」「支付失败」「已取消」等状态时直接跳过 |
| 淘宝、京东等 App 内支付 | ⭐ 很低 | 淘宝明确屏蔽无障碍，首期不支持 |
| 银行 App、云闪付、美团支付等 | ⭐ 很低 | 首期只做支付宝 + 微信 |
| 境外支付、多币种 | ❌ 不支持 | 首期只处理人民币 |
| 手机重启 / 系统杀后台后 | ⚠️ 会漏 | 需要用户重新打开无障碍服务；App 里会做状态检查和提醒 |

> **一句话总结：** 支付宝/微信的“支付成功页”是主战场，能覆盖日常大多数扫码消费；但不要期待它像银行流水一样 100% 完整。

### 3.1 首期范围（已拍板，按两批交付）

| 批次 | 场景 | 交付方式 | 说明 |
|---|---|---|---|
| 第一批（核心） | 支付宝/微信：扫码付、付款码、App 内线上支付成功页 | 自动入账 | 首期先把这一批做稳，这是“无感”的主战场 |
| 第二批（同版本） | 支付宝/微信：转账成功页 | 自动入账（仅“转出”记支出；“转入”默认不记，可开关） | 转账给个人属于人情往来，是否自动记可在设置里关 |
| 第二批（同版本） | 支付宝/微信：红包（发出/收到） | 半自动确认（推荐） | 红包流程特殊，往往要重新点开红包才看得到金额；先做到“识别到就提醒确认”，不强行静默 |
| 后续可选 | 账单详情补记 | 首期不做 | 你担心误识别，先不做；以后需要时再单独评估 |
| 后续可选 | 账单文件导入（方案 C） | 不做进首期 | 你说一般不用账单导入，因此不占首期工期；以后需要再加 |

> 红包**首期建议用“半自动确认”而不是静默自动记**：红包金额经常要重新点开才看得到。如果你希望红包也完全静默，需要接受更高的误记风险，在 P-A0 看样本后再定。账单详情补记按你的要求**首期不做**，避免翻旧账时批量误识别。

## 4. 三种可行方案对比（已选定组合方案）

### 方案 A · 无障碍读屏（推荐）

**通俗解释**：给 App 配一个“速记员”，只在你打开支付宝/微信的支付结果页时，读取页面上的文字并自动记账。

| 维度 | 说明 |
|---|---|
| 自动程度 | ⭐⭐⭐ 最高，最接近你要的「无感」 |
| 覆盖范围 | ⭐⭐⭐ 支付宝/微信扫码、线上支付为主，转账可扩展 |
| 准确率 | ⭐⭐ 中高（取决于页面和规则，需要持续维护） |
| 隐私侵入 | ⭐⭐ 较高（安卓系统会警告“可读取屏幕内容”，但我们只监听支付宝/微信两个包，且本地处理） |
| 开发难度 | ⭐⭐ 中等（服务本身不难，难在页面规则和防重复） |
| 维护成本 | ⭐⭐ 中高（支付 App 改版可能需要更新规则） |
| 适合度 | ✅ **最适合“无感自动记账”的目标** |

**优势：**
- 最接近“付完款什么都不用做，账本就多一笔”的体验。
- 支付宝/微信的支付结果页一般都有金额和商户名，识别成功率较高。
- 已有大量商用产品验证可行。

**劣势：**
- 需要用户手动开启无障碍权限，系统提示比较吓人。
- 国产手机（华为、荣耀、小米、OPPO、vivo 等）可能杀后台，需要引导用户开自启动、省电白名单。
- 支付 App 改版会导致规则失效，需要偶尔更新 App。
- 淘宝等 App 屏蔽无障碍，覆盖不了。

---

### 方案 B · 通知监听（作为补充，不单独做主方案）

**通俗解释**：不读屏幕，只“听”支付宝/微信弹出来的「支付成功」通知，从通知文字里提取金额。

| 维度 | 说明 |
|---|---|
| 自动程度 | ⭐⭐ 中等 |
| 覆盖范围 | ⭐⭐ 窄（不是每笔支付都有通知，通知还可能被合并/折叠/关掉） |
| 准确率 | ⭐ 低到中（通知里经常没有商户名，甚至没有金额） |
| 隐私侵入 | ⭐⭐ 中（需要“通知使用权”，能看到所有 App 的通知） |
| 开发难度 | ⭐ 低 |
| 维护成本 | ⭐ 低 |
| 适合度 | 适合作为方案 A 的**兜底**：A 没抓到但通知里有，就补一条待确认 |

**优势：**
- 实现简单，权限提示比无障碍温和一些。
- 可以作为无障碍漏记时的第二道网。

**劣势：**
- 很多支付没有通知，或通知内容不完整。
- 用户清理通知、开静默模式、系统折叠通知都会导致漏记。
- 无法可靠区分退款、收款、转账。

---

### 方案 C · 账单导入 / 截图 OCR（半自动兜底）

**通俗解释**：不实时监听，而是定期从支付宝/微信导出账单文件导入，或在你打开账单详情页时截图识别。

| 维度 | 说明 |
|---|---|
| 自动程度 | ⭐ 低（需要你手动操作） |
| 覆盖范围 | ⭐⭐⭐ 最全（官方账单最完整） |
| 准确率 | ⭐⭐⭐ 最高（以官方账单为准） |
| 隐私侵入 | ⭐ 低（手动触发，数据可控） |
| 开发难度 | ⭐⭐ 中等（导入解析 + OCR） |
| 维护成本 | ⭐ 低 |
| 适合度 | 作为“补账/对账”兜底，不满足“无感”主诉求 |

**优势：**
- 最准确、最完整，适合每月对一次账。
- 不依赖页面改版。

**劣势：**
- 不是自动，无法做到“付完就记”。
- 支付宝/微信账单导出有时间范围和格式限制。
- 如果加截图 OCR，需要额外引入 OCR 库，App 体积和耗电会增加。

---

### 📊 三种方案对比总览

| 对比维度 | A 无障碍读屏 | B 通知监听 | C 账单导入/OCR |
|---|---|---|---|
| 自动程度 | ⭐⭐⭐ 高 | ⭐⭐ 中 | ⭐ 低 |
| 日常消费覆盖 | ⭐⭐⭐ 支付宝/微信 | ⭐⭐ 部分通知 | ⭐⭐⭐ 全量（但手动） |
| 准确率 | ⭐⭐ 中高 | ⭐ 中低 | ⭐⭐⭐ 高 |
| 隐私侵入感 | ⭐⭐ 较高 | ⭐⭐ 中 | ⭐ 低 |
| 开发工作量 | 约 5~8 个工作日（MVP） | 约 2~3 个工作日 | 约 3~5 个工作日 |
| 长期维护 | 需要跟支付 App 改版 | 低 | 低 |
| 适合你的“无感”目标 | ✅ **主方案** | ✅ **补充** | ✅ **兜底** |

### 🎯 我的推荐

**方案 A 为主 + 方案 B 作为补充 + 方案 C 作为兜底。**

理由：
1. 你的核心诉求是「无感」。只有方案 A 能在支付完成的当下自动读出页面信息并记账，方案 B/C 都做不到。
2. 方案 A 的缺点（系统杀后台、页面改版）可以用“健康检查 + 待确认 + 撤销 + 通知监听兜底”来降低影响，不需要牺牲主体验。
3. 不建议一上来就做“全部场景 + 100% 自动化”。先把支付宝/微信的支付成功页做稳，再按第二批扩展转账和红包；账单详情补记按你的要求暂不做。

> **已按你的选择定稿：** A 无障碍读屏为主，B 通知监听作为兜底，C 账单导入做成后续可选（你说一般不用，所以不占首期工期）。

## 5. 推荐方案的产品设计：智能无感

### 5.1 三种入账方式（已选定：智能无感）

| 模式 | 怎么工作 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **智能无感（推荐）** | 高置信度自动入账；低置信度转「待确认」并通知；通知可撤销 | 兼顾无感与准确，误记最少 | 偶尔还是需要你点一下通知 | 你的“无感”目标 |
| **纯静默** | 只要识别到金额就自动入账，不打扰 | 最无感 | 分类错、金额错时你事后才发现 | 只想彻底无感、愿意事后核对 |
| **悬浮窗确认** | 识别到后弹出一个小窗，你点「保存」才入账 | 最准确，不会误记 | 不是无感；部分手机支付保护会挡住悬浮窗，要退出支付页才弹 | 对准确率要求极高 |

**按你的选择，默认「智能无感」。** 高置信度（金额 + 商户 + 支付成功 + 交易单号/稳定指纹）直接记；只看到金额、没看到商户的，先记一笔并标记「待完善」，通知你点一下选分类；连金额都没读到的，不记，只提醒你补记。

### 5.2 识别成功后的体验

1. 支付完成约 1~2 秒，账本里出现一笔：`支出 ¥12.50 · 餐饮饮食/零食饮料 · [自动] 星巴克`。
2. 手机通知栏出现一条低打扰通知：`已自动记账 ¥12.50 · 星巴克`，带两个按钮：
   - **撤销**：这笔进回收站（可恢复），5 分钟内可点。
   - **改分类**：打开 App 的编辑弹窗，改完自动记住这家商户。
3. 首页「最近记录」和账单页会显示一个浅色的「自动」小标签，方便你区分手动记录。
4. 如果通知权限没开：不弹通知，但下次打开 App 时在「自动记账」页能看到「最近自动记录」列表和「待完善」项。

### 5.3 待确认 / 待完善

- 金额读到、商户没读到：记为「待完善」，默认分类可设置（例如「其他杂项/其他」），通知提醒你补商户/分类。
- 金额没读到：不记账，只生成一条「识别到一笔支付，但没读到金额」的提醒，点开可手动补。
- 同一页面反复出现：只处理一次，不重复提醒。

### 5.4 自动记账专属页面

在首页页脚新增一行「自动记账」，点进去是设置页：

- **总开关**：开 / 关。
- **权限状态卡**：无障碍服务（已开启/未开启）、通知权限、悬浮窗（仅确认模式需要）、电池优化（是否已忽略）。
- **支持的 App**：支付宝、微信（各自开关）。
- **入账方式**：智能无感 / 纯静默 / 悬浮窗确认。
- **默认分类**：不认识商户时用哪个分类。
- **商户规则**：查看、添加、编辑、删除「商户关键词 → 分类」规则。
- **最近自动记录**：最近 20 条，带「撤销 / 改分类 / 查看原页面样本（仅调试版）」。
- **服务健康**：上次识别时间、上次入账时间、服务是否还活着；提供「去修复」按钮。
- **隐私说明**：用大白话写清楚“看什么、不看什么、数据去哪了”。

## 6. 分类怎么自动判断（决定好不好用）

自动记账如果分类总是错，最后还是要你一条条改，就不算“无感”。建议三层规则：

1. **内置常用商户库**：例如
   - 餐饮：美团、饿了么、肯德基、麦当劳、星巴克、瑞幸、蜜雪冰城、餐厅、饭店、咖啡、奶茶……
   - 交通：滴滴、高德打车、曹操出行、地铁、公交、加油、充电、停车、12306……
   - 购物：淘宝、天猫、京东、拼多多、超市、便利店、盒马……
   - 娱乐：电影、猫眼、淘票票、KTV、游戏充值……
   - 医疗：药房、医院、诊所、体检……
2. **用户自定义规则**：在「商户规则」里手动添加“包含某个关键词 → 某个二级分类”。比如“公司楼下那家咖啡店 → 餐饮/零食饮料”。
3. **从修改中学习**：你每次修改自动记录的商户分类，弹一个“以后这家都这样记？”的确认（默认勾选），下次自动按你的选择分类。

**兜底：** 实在认不出的商户，记到你设置的「默认分类」，并标「待完善」提醒你补。不要因为认不出分类就不记账——先记下来，比漏记好。

## 7. 防重复、防误记（重点）

自动记账最怕两件事：**同一笔记两遍**、**把退款/失败也记成支出**。方案里设计五道锁：

1. **只认正向状态**：页面必须出现「支付成功 / 付款成功 / 交易成功」，出现「支付失败 / 已取消 / 交易关闭 / 退款」等一律跳过。
2. **先等页面稳定**：支付结果页弹出来时文字会分批加载，等 0.8~1.5 秒再读，同一页面只解析一次（防抖）。
3. **交易单号优先**：能读到「订单号 / 交易单号 / 商户单号 / 交易号」就用它做唯一键；读到过就永远不重复记。这样你以后翻旧账单详情页也不会重复入账。
4. **金额+商户+时间指纹**：读不到单号时，用“金额 + 商户 + 10 分钟时间窗”做指纹，相同的只记一次。日志保留 90 天。
5. **通知可撤销 + 自动标签**：万一还是记错了，通知栏一键撤销；账单列表显示「自动」标签，方便你定期核对。

另外，同一天在同一家店买两笔相同金额的东西（比如两杯咖啡）不会被误合并：如果两次都有交易单号，各记各的；如果没有单号，两次之间至少间隔 10 分钟才会分别记，10 分钟内完全相同金额+商户的第二次可能被当成重复——这是取舍，会在隐私/设置页说明。

## 8. 权限与隐私

### 8.1 需要哪些权限

| 权限 | 用途 | 是否必须 | 用户感知 |
|---|---|---|---|
| 无障碍服务 | 读取支付宝/微信支付页文字 | ✅ 必须 | 系统高危提示，需手动开启 |
| 通知权限 | 显示“已自动记账/可撤销”通知 | 建议开启 | 普通通知权限 |
| 通知使用权 | B 方案兜底：读取支付宝/微信的支付通知 | 可选（B 兜底需要） | 系统“通知使用权”设置，能看到所有 App 通知 |
| 悬浮窗权限 | 只在「悬浮窗确认」模式需要 | 可选 | 普通“显示在其他应用上层” |
| 忽略电池优化 | 降低后台被系统杀掉概率 | 建议开启 | 系统设置里手动确认 |
| 网络权限 | 已有，用于账单云同步 | 已有 | — |

**不需要：** 读取短信、通讯录、位置、麦克风、相机、存储卡全盘权限。自动记账本身不申请这些。

### 8.2 隐私承诺（会写进 App 的说明页）

- 只监听支付宝（`com.eg.android.AlipayGphone`）和微信（`com.tencent.mm`）两个包，其他 App 的页面一律不处理。
- 只在识别到“支付成功/付款成功”等页面时才读取文字；不保存完整屏幕内容。
- 所有识别在本机完成，**不上传页面原文、不上传截图**；只同步最终生成的那条账单（和手动记账一样）。
- 不点击、不滑动、不代替用户操作支付 App。
- 关闭开关后立即停止；清除数据时一并清除自动记账日志和规则。
- 调试版的「页面样本导出」默认关闭，只有你主动点「导出样本」才会生成脱敏文本文件，且由你自己决定要不要发给我。

### 8.3 安卓 13+ 的「受限制的设置」

因为你安装的是直接发送的 APK（不是应用商店），Android 13 及以上可能限制无障碍权限。开启路径：

1. 设置 → 应用 → 计序 → 右上角 ⋮ → 「允许受限制的设置」。
2. 再回设置 → 无障碍 → 已安装的服务 → 计序 → 打开。
3. 不同品牌路径略有不同（小米/华为/OPPO/vivo 都有差异），App 内会提供图文引导。

### 8.4 不冒充“无障碍工具”

Google 对 `isAccessibilityTool=true` 有严格定义，只有真正服务残障人士的工具才能声明。自动记账不属于这一类，所以不会冒充；系统提示“此服务可读取屏幕内容”是正常的，用户需要知情同意。

> 长期风险：Android 17 的“高级保护模式”会把无障碍服务限制为“已验证的无障碍工具”，开启该模式的手机可能无法使用自动记账；这是可选模式，普通用户不开启就不受影响。另外 Android 14+ 允许支付 App 把某些界面标记为“无障碍敏感”，未来若支付宝/微信采用，可能导致读不到部分文字，届时需要 OCR 兜底或接受限制。详见 §11。

## 9. 分阶段开发计划

> 当前只做评估，不改代码。下面每个阶段都要你确认后才进入下一阶段。

### P-A0 · 探针与真实样本采集（1~1.5 天）

**做什么：**
- 在调试版 APK 里加一个「自动记账探针」页面（正式版不显示）：
  - 显示当前前台 App 的包名、页面标题。
  - 把当前页面的文字节点按层级列出来（金额、商户、按钮文字等）。
  - 提供「复制/导出样本」按钮，生成一个脱敏文本文件（不含账号、手机号、余额等无关信息）。
- 你用支付宝/微信合计做 15~25 笔小额支付（0.01 元即可），覆盖：扫码付、付款码、线上付、转账（转出/转入）、红包（发出/收到）、失败/取消、退款（如有）。
- 把样本发给我，我分析支付宝/微信当前版本的页面结构。

**过关标准：**
- 能拿到至少 15 个真实页面样本（支付成功页、转账页、红包页各若干）。
- 能确认金额、商户、状态在页面文字里找得到。
- 如果发现关键页面读不到文字（例如被标记敏感或被 WebView 屏蔽），则暂停，重新评估 OCR/通知监听方案。

**为什么先做这个：** 没有你手机上的真实页面样本，任何规则都是“猜”的；这一步花半天，能避免后面返工。

### P-A1 · 解析核心 + 单元测试（2~3 天）

**做什么：**
- 定义页面快照数据结构（`PageSnapshot`）和解析结果（`ParsedPayment`）。
- 用 P-A0 的样本做测试夹具，实现：
  - 页面类型判断（支付成功页 / 转账 / 红包 / 失败页）
  - 金额提取（支持 `¥12.50`、`￥12.50`、`12.50元`、`1,234.56` 等格式，排除优惠金额、余额）
  - 商户提取（收款方/商户全称/付款给/转账给/红包发送对象）
  - 交易单号提取（订单号/交易单号/商户单号/交易号）
  - 状态判断（成功/失败/取消/退款）
  - 方向判断（转账转出/转入、红包发出/收到）
  - 置信度评分
- 纯 Kotlin，不依赖安卓界面，全部可跑 JVM 单元测试。

**过关标准：**
- P-A0 采集的每个样本都有对应测试用例。
- 金额识别 100% 正确（样本范围内）；商户识别 ≥90%；失败/退款样本 100% 不误记。

### P-A2 · 无障碍服务 + 权限引导 + 设置页（2~3 天）

**做什么：**
- 新增 `AutoBookAccessibilityService`，只监听支付宝/微信两个包，只处理窗口变化/内容变化事件。
- 新增 `AutoBookScreen` 设置页：总开关、权限状态、支持 App、入账方式、默认分类、隐私说明。
- 首页页脚加「自动记账」入口。
- 权限引导：无障碍、通知、悬浮窗（可选）、电池优化、Android 13 受限制设置。
- 服务健康检查：显示「服务运行中 / 已关闭」，提供「去开启」按钮。
- 调试版保留「探针」入口。

**过关标准：**
- 真实手机上能手动开启无障碍服务。
- 打开支付宝/微信支付成功页，探针能看到页面文字。
- 关闭开关后服务不再处理任何页面。

### P-A3 · 自动入账 + 分类规则 + 撤销/待确认（3~4 天）

**做什么：**
- 解析成功后调用 `Repository.addRecord`，写入 `[自动] 商户名` 备注和「自动」标记。
- 商户 → 分类规则库（内置 + 用户自定义 + 修改学习）。
- 自动记账日志表（防重复、90 天清理）。
- 通知栏「已自动记账 · 撤销 / 改分类」。
- 待完善列表（商户缺失、分类未知）。
- 设置页「最近自动记录」列表。
- 转账：仅“转出”自动记支出；“转入”默认不记，可在设置里打开。
- 红包：识别到金额后半自动确认（通知/待确认列表），不静默入账。
- 处理同商户多次支付、同金额多笔、退款/失败等边界。

**过关标准：**
- 10 笔真实支付中，≥8 笔自动入账成功，金额全部正确。
- 转账转出能记、转入不误记；红包能走“确认后入账”流程。
- 同一笔支付不会重复入账（反复进出支付页、重复通知、重启 App 均验证）。
- 撤销后账本恢复原状；改分类后下次同商户自动分类正确。
- 失败/取消/退款样本 0 误记。

### P-A4 · 通知监听兜底 + 稳定性、省电与真机兼容（2~3 天）

**做什么：**
- 新增 `AutoBookNotificationListenerService`（方案 B 兜底）：申请“通知使用权”，只读取支付宝/微信的支付通知；通知里能解析出金额/商户就补一条待确认，不静默入账。
- 服务被杀后的健康提醒（复用现有 AlarmManager/通知基础设施，每天检查一次）。
- 国产手机（小米/华为/荣耀/OPPO/vivo）自启动、省电白名单的图文引导。
- 事件过滤和性能优化，确认日常使用不发热、不明显耗电。
- 隐私说明页、清除数据联动（清空自动日志和规则）。
- release 包 R8 混淆验证（无障碍服务、通知监听服务类不能被混淆掉）。

**过关标准：**
- P-A0 中 A 读不到的支付页，B 通知监听能在有通知的情况下补上待确认项。
- 锁屏 8 小时后服务仍正常（测试机）。
- 日常使用一天耗电增加 < 2%。
- 关闭/开启无障碍、通知使用权、重启手机后状态显示正确。
- release 包功能与 debug 包一致。

### P-A5 · 真机验收 + 打包（2~3 天，含你测试的时间）

**做什么：**
- 用 release APK 在你的手机上跑完整验收清单（见下）。
- 修复验收发现的问题。
- 版本号升到 `1.0.1` / versionCode 2，重新打包。
- 更新 `开发文档.md` 和 `执行计划.md`，把自动记账模块正式纳入。

**验收清单（你按清单点）：**
- [ ] 支付宝扫码付 ¥0.01 → 1~2 秒内自动出账，金额正确。
- [ ] 微信扫码付 ¥0.01 → 自动出账。
- [ ] 支付宝线上支付一笔 → 能记（或至少进待确认）。
- [ ] 支付宝/微信转账转出一笔 → 自动记支出；转入一笔 → 默认不记。
- [ ] 发/收红包一笔 → 走“确认后入账”，不静默误记。
- [ ] 支付失败/取消 → 不记账。
- [ ] 同一笔反复进出支付页 → 只记一次。
- [ ] 点通知「撤销」→ 这笔进回收站，可恢复。
- [ ] 修改一笔自动记录的商户分类 → 下次同商户自动分类正确。
- [ ] 关闭自动记账开关 → 不再自动记录。
- [ ] 手机重启 → 无障碍服务状态正常；被系统关掉时 App 有提醒。
- [ ] 飞行模式记一笔 → 本地立刻出现，联网后自动同步到电脑/小程序。

### P-A6 · 可选增强（后续再定，不在首期）

- 截图 OCR 兜底（需要你另选 OCR 库方案）。

- 多设备同步「自动规则」（目前建议规则只存本机，不跨端）。
- 账单详情页提示式补记（你担心误识别，首期不做；以后要单独评估风险后再加）。

### A.3 页面快照与解析

```kotlin
data class UiNode(
    val text: String,
    val contentDescription: String,
    val viewId: String,
    val className: String,
    val bounds: Rect,
    val depth: Int,
    val indexInParent: Int,
)

data class PageSnapshot(
    val packageName: String,
    val windowTitle: String,
    val nodes: List<UiNode>,
    val capturedAt: Long,
)

data class ParsedPayment(
    val platform: Platform,      // ALIPAY / WECHAT
    val amountCents: Long,
    val merchant: String?,
    val orderId: String?,
    val status: PayStatus,       // SUCCESS / FAILED / CANCELLED / REFUND / UNKNOWN
    val pageType: PageType,      // PAY_RESULT / TRANSFER / RED_PACKET（账单详情首期不做）
    val confidence: Double,      // 0.0~1.0
)
```

解析流程：
1. 从 `AccessibilityNodeInfo` 根节点深度优先展开，只保留 `isVisibleToUser == true` 的节点。
2. 文本归一化（全角转半角、去空格、去千分位逗号）。
3. 先用关键词判断页面类型和支付状态；失败/取消/退款直接返回 `IGNORED`。
4. 金额候选：正则 `[¥￥]\s*([0-9][0-9,]*(\.[0-9]{1,2})?)|([0-9][0-9,]*(\.[0-9]{1,2})?)\s*元`。
   优先级：带「实付 / 付款金额 / 支付金额 / 合计」标签的节点 > 紧邻「支付成功」的金额 > 页面主区域的唯一金额；明确排除「优惠 / 红包 / 抵扣 / 余额 / 余额宝」附近的数量。候选按“距离「支付成功」文字的纵向距离 + 是否在页面上半部 + 字号（若可获取）”打分。
5. 商户候选：找「收款方 / 商户全称 / 付款给 / 转账给 / 商户名称」标签后的节点；找不到则取页面标题。
6. 订单号候选：`(订单号|交易单号|商户单号|交易号)[:：]?\s*([A-Za-z0-9]{8,})`。
7. 置信度 = 金额命中(0.4) + 正向状态(0.3) + 商户(0.2) + 订单号(0.1)。

### A.4 防重复数据模型

```kotlin
@Entity(tableName = "auto_captures")
data class AutoCaptureEntity(
    @PrimaryKey val id: String,          // a_<毫秒>_<随机>
    val platform: String,                // alipay / wechat
    val pageType: String,
    val amountCents: Long,
    val merchant: String?,
    val orderId: String?,
    val fingerprint: String,             // package|amount|merchant（时间窗另按 capturedAt 查，不放进指纹）
    val capturedAt: Long,
    val status: String,                  // RECORDED / PENDING / IGNORED / FAILED
    val recordId: String?,               // 写入后的本地账单 id
    val confidence: Double,
)

@Entity(tableName = "auto_rules")
data class AutoRuleEntity(
    @PrimaryKey val id: String,
    val platform: String?,               // null = 全部
    val keyword: String,                 // 商户关键词
    val categoryKey: String,
    val categoryName: String,
    val subcategoryKey: String,
    val subcategoryName: String,
    val priority: Int,                   // 用户规则 100，内置 10
    val hitCount: Int = 0,
    val lastUsedAt: Long? = null,
)

@Entity(tableName = "auto_pending")
data class AutoPendingEntity(
    @PrimaryKey val id: String,
    val platform: String,
    val amountCents: Long?,
    val merchant: String?,
    val rawHint: String?,
    val capturedAt: Long,
    val status: String,                  // WAITING / RESOLVED / DISMISSED
)
```

可选：给 `RecordEntity` 增加两个**只存本机、不上云**的字段：
- `origin TEXT DEFAULT 'manual'`（manual / auto）
- `auto_capture_id TEXT NULL`

`localToCloud` 不输出这两个字段，`cloudToLocal` 不读取它们，因此不会影响三端同步。若不想改 Room 表，也可以先用 `note` 前缀 `[自动]` 区分，但列表标签和撤销关联会更麻烦，建议加字段。

### A.7 隐私/安全检查清单

- [ ] 只 `packageNames` 支付宝/微信；不监听其他 App。
- [ ] 不保存完整 `AccessibilityNodeInfo` 树到磁盘；只保留当前解析所需字段，内存中使用后丢弃。
- [ ] 不把页面文本写入日志（正式版关闭 `Log.d` 输出页面内容）。
- [ ] 调试版「导出样本」默认关闭；导出前脱敏（去掉手机号、账号、余额、订单号部分位数）。
- [ ] 不申请短信、通讯录、定位、麦克风、相机、存储全盘权限。
- [ ] 不调用 `performAction` / `dispatchGesture`，只读不操作。
- [ ] 通知「撤销」只对自动记账产生的记录生效（校验 `recordId` / `auto_capture_id`）。
- [ ] 清除数据时一并清除自动记账全部本地数据。

### A.8 版本与兼容

- Room `version = 2`，新增三张表和可选两个字段；用 `Migration(1, 2)` 写 `ALTER TABLE`，老用户升级不丢数据。
- `versionCode` 从 1 升到 2，`versionName` 1.0.0 → 1.0.1（或 1.1.0，按发布策略）。
- `targetSdk` 保持 36；无障碍配置从 API 26 起可用；`canTakeScreenshot` 仅 API 30+（如果后续加 OCR）。
- release 包开启 R8 时，检查无障碍服务类、`AndroidManifest` 的 meta-data、Room 实体不被混淆（保留规则或 `@Keep`）。
